Architecture

Real time, without the waiting.

A native Rust app in two halves: an egui interface that can redraw, load and save at its own pace, and an audio engine that never waits for it.

On this page Two threads The engine Plugins and MIDI Performance Source tree Adding a module Stack

01Two threads

The UI never blocks the audio thread. Knob values travel through atomics, read by the engine as it runs. Structural changes (nodes added or removed, a new processing order) reach the engine as commands on a channel.

Buffers that take memory (a delay line, a reverb, a granular loop) are allocated on the UI thread when the node is created. Removed nodes and old processing orders are handed back to the UI thread to be freed: freeing memory inside the audio callback (a delay line is megabytes) could stall it into a click. A sample loaded into a Splitter goes the same way (audio/sample.rs): the UI swaps it in under a lock and bumps a version; the processor takes it with try_lock, never waiting (it tries again next block), and hands back the one it let go, to be freed by the UI.

On the UI side, graph.rs holds the patch model (nodes, cables, modules) and orders it with Kahn's algorithm; on the audio side, engine.rs runs the precomputed topological order.

02The engine

  • One pass per device buffer. Built-in nodes run through it in 64-frame stereo blocks, so MIDI timing and modulation stay fine-grained.
  • MIDI per block: events land in the block they belong to; the global clock counts in beats, so every sequencer shares one grid.
  • Lookahead limiter at the end, just under full scale, so a loud sum is turned down instead of clipped.
  • Denormals flushed to zero, and per-sample maths on fast approximations of sine, exp2, log2 and tanh (error under 1e-6).
  • A new sample rate builds a new engine; the patch, its settings and cables stay.
  • 2× oversampling (a half-band FIR) is shared by Magma, Tape, Aether and Prism.

03Plugins and MIDI

A plugin gets the whole buffer in a single call, with its MIDI events placed at their exact offsets, since every plugin call has a fixed cost. A heavy instrument costs the same whatever the patch around it.

Plugins of both formats sit behind one lock, used with care: the UI calls into a plugin only between audio callbacks (when the audio thread has just finished and won't need it for most of a buffer), one call at a time, at most ten times a second. A plugin's complete state is read only when saving, so the audio thread is not kept waiting.

Audio Units are hosted through audio/au_host.m, a small Objective-C layer over AUAudioUnit that build.rs compiles with the cc crate on macOS. It uses manual reference counting, so nothing on the render path retains, releases or allocates; audio/au.rs is its Rust face. AUv3 extensions are opened out of process, as macOS does by default, so a crash there leaves the board playing; classic AU components run in process. An Audio Unit has no file, so it travels as a pseudo-path (audiounit:<type>-<subtype>-<maker>, in hex) wherever a plugin path goes. Its parameters are set from the UI directly (AUParameter is thread-safe), not through the audio thread.

Plugin nodes (audio/node_plugin.rs) are AudioBoard's own format: nodes written against the node SDK (crates/audioboard-node) and built into a dynamic library. App and plugin share only a C ABI, since Rust has none of its own: #[repr(C)] tables and extern "C" functions, whose first field is a version the app checks before reading anything else. A library is opened with libloading, its description copied and checked, and each node registered, lock-free, as one more kind of module (ModuleKind::Ext): the generic panel, presets, MIDI mapping and projects (by a stable id) come with it. On the audio thread a plugin node is called once per 64-frame block with nothing but pointers: its buffers, its MIDI, its settings' atomics. A panic is caught at the boundary and silences only that node; non-finite samples are muted. Libraries are never unloaded, since live nodes run their code. The SDK page shows how to write one.

MIDI inputs (midir) connect automatically, even when plugged in after launch, and feed shared state read by the MIDI nodes, including a MIDI clock and transport for the MIDI Looper.

MIDI sync (audio/sync.rs): the chosen input's thread times the clock with a least-squares fit over the last beat of ticks, for the tempo and the phase, and publishes it lock-free (seqlocks). Each callback, the engine steers its beat onto the clock's, nudging its rate by a few percent and jumping only when far out or on Start, Continue and song position. To send a clock, the engine publishes its timeline every callback and a thread of its own sends ticks, Start, Stop and song position, timed to leave when their beat is heard.

04Performance

  • Effects rest when quiet. With a silent input, once their own echoes and tails have stayed below −100 dB for as long as they can remember sound, they skip their work until input returns. A frozen reverb or an endless delay never rests.
  • Stopped sources rest too, so a stopped patch costs almost nothing once its tails are gone.
  • Nodes nobody hears rest. The processing order marks which nodes reach the device through cables, audio or MIDI; any other node runs 2 seconds more (a cable moved to another input comes back seamlessly), then is skipped until it is heard again, carrying on from its state with a 20 ms fade-in. What is heard stays the same, bit for bit. The MIDI Looper, MIDI CC, MIDI Note and Iris always run.
  • The UI redraws at full rate only during interaction and animations; meters, analyzers and step lights update at 30 fps, and not at all while the window is minimized.
  • Zoom uses font sizes rounded to half a point, so animations don't re-create glyphs every frame; from far away, unreadable text is not drawn and the grid is a single mesh.
  • Auto layout and zoom transitions follow a spring curve with no bounce: nodes set off in a wave from left to right, and zoom proceeds on a logarithmic scale around the centre.

06Adding a module

  1. A file in audio/modules/ with its ModuleDef (knobs, ports, modes, toggle) and a Processor.
  2. An entry in ModuleKind.
  3. In ui/modules.rs, the readout and the display.

The panel (ports, selector, knobs) is generated from the definition. Larger instruments draw their own: Frakture, the Equalizer, Prism, Magma, Tape, Nullpunkt, Aether, Larsen, Vesper, the MIDI Looper, Automa, Colloid, Orrery, Fjord, Splitter, Iris (sized by the user) and Pops 66, whose sizes, like Fjord's, follow their settings through modules::size_of. Frakture's hexagon runs on the audio thread, block by block: the panel hands it the mouse through the module's display values, so paths keep time even when the window doesn't redraw.

A node that should ship on its own is a plugin node instead, and needs no change to the app: see the SDK page.
